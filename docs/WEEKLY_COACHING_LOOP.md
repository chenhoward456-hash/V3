# 設計：每週教練監督迴圈（撐月費的核心）

> 來源：2026-06-14 office-hours 腦力激盪。Howard 拍板方向。
> Status: DRAFT — 待選方案後落地。

## 問題
血檢一年才 2-4 次，撐不起月費。「健康管理平台＝營養+訓練+恢復+血檢」是**功能清單，不是價值主張**——每項單獨都有更便宜對手（MFP/TrainHeroic/Whoop/Function）。功能堆疊 ≠ 非訂不可。

## 真正撐月費的「工作」
> 「有一個懂我數據的教練，**每週**盯著我、為我調整、逼我朝目標前進，我不用自己搞懂。」

- 營養/訓練/恢復/血檢 = 教練**管理的表面積**（材料），不是賣點。
- 賣點 = **持續的監督與調整本身** + 它是 **Howard 的判斷**（護城河：別人抄得了功能，抄不了 Howard）。
- 北極星記憶佐證：唯一留存者陳胤豪 = 每天餵數據 + 系統有反應 + 推播召回。迴圈閉上才留人。

## 核心概念：每週教練動作（Weekly Coaching Action）
每週一次，對每個活躍學員：
1. **系統合成這週**：體重 vs 目標(trajectory)、飲食合規、訓練進步/停滯(TrainingProgress 引擎)、恢復(wellness/wearable)、新血檢(if any)。
2. **系統草擬調整 + 白話理由**：macro/訓練/聚焦點的本週建議（「碳水 -15g、加一組腿、今天先別 deadlift，因為__」）。
3. **進 Howard 核准佇列**（1 對 50 的槓桿）：批次掃過，一鍵 核准/微調/跳過。Howard 的判斷蓋章（可覆寫 AI、補人味，如揪尿酸）。
4. **交付學員**：核准 → 一則「像 Howard 親自寫的」週度教練訊息（Web Push + 儀表板卡 + 進報告）。**這是月費的每週心跳。**

## 已有的零件（建在現有之上，非從零）
- `/api/cron/weekly`：已生 weekly_summaries + AI 週報（→ 升級成「合成 + 草擬調整」）
- `pending_proposals` 表：AI/系統提案佇列（24h 過期、safety_check_result）——**根本就是為這個核准流設計的**
- `trajectory-adjust` / `nutrition-engine`：macro 調整腦（+ `coach_macro_override` 讓 Howard 改的贏）
- `lib/training-progress.ts`：訓練進步/停滯（剛建）
- admin 行動佇列：教練操作面
- `lib/notify.ts` sendRoutineReminder + Web Push：交付
- 健康報告（HealthReportDocument）：可塞「本週教練調整」

→ **缺的不是能力，是「把全部訊號合成成一個每週的教練動作 + 核准佇列 UX + 個人化交付」**。

## 關鍵設計規則：資料量決定模式（2026-06-14 從真實數據學到）
週動作**必須先偵測這位學員的資料量**，自動切兩種模式。**不可只做「資料滿」版**——多數學員資料是爛的，天真版會吐假調整或空白。

- **調整模式（資料夠）**：有近 1-2 週的體重/飲食/訓練/恢復 → 做數據驅動的教練調整（如陳胤豪：蛋白拉滿、熱量不動、補腿）。
- **問責模式（資料不足/斷記錄）**：近期幾乎沒記錄 → **系統不假裝、不講幹話**，翻成：(a) 對學員「召回 + 先回來記一筆」(b) **標記 Howard：這個要你親自戳，不自動發** (c) 靠最後的硬數據（血檢，不依賴每日打卡）。
  - 真實案例 謝佳峻（2026-06-14）：近 21 天只記飲食 1 天/訓練 1 天/體重 3 天、6/11 後斷 3 天。體重 89.5→87（2 天 -2.5kg）是水分雜訊、不可信 → 系統應判「資料不足」走問責模式，而非硬算。

### 月費迴圈的前提：記錄率
週動作的價值**取決於學員有沒有記錄**。學員付錢可以不遵守——這不是系統缺陷，是**所有教練的宿命 + 問責的接觸面**。系統的責任：
1. 讓記錄爽到他想記（低摩擦 + 即時回饋 + 推播召回）← 陳被勾住的原因
2. 該戳人時標記 Howard（人味介入）
3. 早期預警「誰快流失」（如謝），讓 Howard 選擇介入或放生，而非假裝在教
→ **所以「衝記錄率」＝衝推播開通 + 啟動序列 + 每日回饋迴圈**（本專案已建的留存機制全是在餵這個迴圈的燃料）。

## 方案
### A：最小可行（先證明迴圈）— S/M，低風險
weekly cron 對每個學員草擬「本週一句話調整 + 理由」寫進 `pending_proposals`；admin 加一個「本週教練佇列」批次核准/微調；核准 → push 學員那則訊息 + 進報告。
- Pros：最快、零件幾乎都在、立刻有「每週被教練」的心跳
- Cons：合成邏輯先簡單（單一主調整），不是完整多維

### B：理想（A 養成的終態）— L
專屬「每週教練 console」：每個學員的合成週況（趨勢+旗標）+ 多維建議（macro/訓練/恢復），Howard 批次一鍵核准/編輯，學員收到豐富「週度教練 review」卡。產品的常態心跳。
- Pros：完整 1對50 像 1對1、最強月費錨
- Cons：工大，宜由 A 演進

### C：橫向（事件驅動的 always-on 教練）— M/L
不等每週，數據一變（停滯/恢復掉/血檢來）就以 Howard 名義主動發訊，Howard 核准出去的訊息。更連續、更「隨時有教練」，但難批次、難規模化。

## 推薦
**北極星是 B，先出 A。** A 就是月費心跳的 MVP（草擬→核准→交付），跑通證明槓桿 + 學員「被教練感」上來，再長成 B 的 console。C 的事件驅動之後可疊上去當補充。

## 成功判準
- Howard 每週能在 < 30 分鐘核准完所有學員的調整（1對50 槓桿成立）
- 學員每週收到 1 則個人化教練訊息、開啟率/回訪上升
- 留存：從 1/25 往上動（先看開推播+週訊息的學員週回訪）

## 假設（待驗）
- 學員真的會因「每週被調整/被盯」而續訂（不是因為功能多）→ A 上線後看週訊息開啟 + 續訂
- Howard 願意每週花 ~30 分鐘核准（換來規模）

## The Assignment（Howard 的下一步真實動作）
這週你自己**手動**對 3 個活躍學員做一次「每週教練動作」（看數據→決定調什麼→寫一句話理由發給他），記下：(a) 每個花你幾分鐘 (b) 你都看哪些數據才決定。這份手動流程 = A 要自動化/幫你預填的規格。
